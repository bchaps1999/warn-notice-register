# Deterministic WARN assembly contract

The dataset is assembled from preserved agency WARN source rows and documented parser rules. The supported build admits agency-source evidence under explicit source, identity, and date rules. It may use open-source scraper and parser code to collect agency data. The build makes no LLM API calls, does not replay model decisions, and creates no manual review queues. Historical model experiments and their outputs remain outside the public repository.

## Admission

1. Preserve the source bytes, capture URL and date, artifact hash, row pointer, and raw fields. A source-only rebuild writes an exception manifest for every row it cannot admit and `source_observations.csv` for verified agency observations.
2. Admit a notice when its source adapter produces a canonical row that passes parser and source-specific identity checks. An explicit agency filing ID is preferred. A hash or similarity of employer/date/workers is not a filing ID.
3. The admitted unit is the agency's listed entry. Where the source gives a filing ID (OR `WARN#`, the NY detail-page `Control Number`, IL IEBS, KS), the notice is the filing: itemized site or phase rows go into `source_details.sites[]` or `phases[]` with `effective_date_interpretation: "list_or_phases"`, its workers are the sum of the itemized counts (arithmetic on the agency's itemization only), and its dates run from the earliest to the latest item. NY detail pages repeating one Control Number are that filing's versions in detail-id order. Where the source has no filing ID (CA EDD reports, the NY dashboard, the IA event log, WI/PA/MI logs), the notice is the row. Rows a source ties to one filing carry `source_details.filing_group` and are linked by additive `sibling_entry` links (method `source_group`); counts are never summed across row-unit notices. The archived WI logs list a filing's phases as same-key rows; they become one notice with `phases[]`, and workers are left unsummed when an original row and its update row are both listed.
   - Two distinct rows of one document that share a legacy `dedupe_key` cannot be re-observations over time. For states with `same_key_policy: distinct_rows` in `states.yaml` (CA, PA, MI, NE), `normalize/entries.py` gives every distinct row after the first the key `sha1(legacy_key|entry|[effective_date, employees_affected, layoff_type])` and records `source_details.entry`. The row keeping the legacy key is the one holding the stored notice's current version, else any stored version, else the first in source order, so released keys never change. Identical rows still coalesce. The scope is one document: where a capture joins several documents, `same_key_document_fields` names each row's document (CA: the EDD report's `source_file`, or the annual PDF's `year_file`; NE: the NDOL page), and same-key rows of different documents are a notice re-listed over time (e.g. a corrected count in the next fiscal-year report), so they stay one notice's versions. Other states keep `versions`: same-key rows fold into one notice's versions, and a date disagreement over 45 days holds the whole key group.
   - A WI/FL update row whose content (action date, workers, layoff type, temporary flag) exactly equals an earlier row for the same employer and location becomes a version of that notice; its released key is retired through `data/review/wi-fl-update-transition-2026-09-29.csv` (`migrate/wi_fl_update_transition.py`). Rows with neither an action date nor a worker count are not matched.
   - A NY dashboard row matching exactly one control-number notice on employer group, notice date, workers and county becomes that notice's version (`migrate/ny_annual_source.py`). Where the dashboard row was released as its own notice, its key is retired through `data/review/ny-dashboard-correspondence-transition-2026-09-30.csv` (`migrate/ny_correspondence_transition.py`). A looser match (employer group and notice or action date) holds the dashboard row, except when every candidate is a control-number filing rebuilt from conflicting detail pages (`normalize/entries.control_number_versions`): those filings were held when the dashboard row was admitted, so the row stays its own notice and records the candidates in `source_details.possible_correspondence` (not merged). Such a recovered filing, unless it is an exact version target, is then held as `possible_duplicate_of_admitted_notice` (each of its pages is in the exception manifest with the dashboard notice's key and matched fields), so the already-admitted dashboard notice stays the single record.
   - A version whose filing identity the source establishes (one NY Control Number, one OR `WARN#`, a NY dashboard row matching exactly one control-number notice, an IA row declared as an amendment with a single parent at its site) is ingested with its key in `revision_keys`, so a moved action date is recorded as that filing's revision instead of tripping the 45-day same-key collision hold.
   - An IA amendment version builds on the notice's latest version in source order and is listed in `source_details.amendments[]`. Its layoff date applies only for a "Change in date" type and its worker count only when the type states a restated total (no event-log type does); otherwise the notice keeps its count, and a notice with more than one amendment has `worker_allocation: "unresolved"`. An OR filing is summed over its listed rows only when each row is a distinct site (Company Name and Location) and date; repeated site/date rows leave the total unknown (`worker_allocation: "unresolved"`).
   - The live scrape (`pipeline.py`), the raw replay (`clean_rebuild.build`) and the archive replay (`offline_rebuild._cached_agencies`) apply these rules at the same point, before `dedupe.split_collisions`, so the same rows receive the same keys.
   - GA, IA, KS, and NJ adapters exclude ambiguous same-key groups with stable reason codes; other source-specific rules may exclude rows that cannot be interpreted. Source-only rebuilds record every exclusion in the exception manifest. Missouri rapid-response rows stay held and are exported as `source_observations` with status `identity_unresolved`; Nebraska rows listed on NDOL's layoff/closure report rather than its WARN report are exported with status `not_in_agency_warn_report` (where the row is listed, not a finding that the event was not a WARN event). No queue or later human action is assumed.
4. Missing optional facts do not exclude an otherwise identifiable notice. Preserve the employer and location as filed; leave unsupported dates, worker counts, geography, industry, and historical parent relationships null or explicitly unknown. A date-shaped string does not prove its legal role or precision.
5. A source-specific, hash-guarded rule may add a field or relationship only when the source states the needed fact. Name similarity, date proximity, or an amendment marker alone cannot establish a link between two events.

## Outputs and coverage

The database, national/state CSVs, site data, source-observation export, and exception manifest must agree. Report admitted and excluded source rows by state, source, year where known, and reason. The published totals describe **admitted notices**, not all WARN filings in the country; known historical and source-format gaps must remain visible. An excluded observation is a final conservative disposition for the current evidence, not an item awaiting review.

## Rebuild and release checks

- Pin dependency and reference versions, source bytes, code revision, and an explicit `--as-of` date for site output. Rebuild from a fresh checkout without network access after inputs are frozen.
- Check that every raw source row is represented as an admitted notice, a linked exact duplicate/version, or an explicit exclusion. Reject format drift, same-key disagreement, and source-hash mismatch rather than silently changing totals.
- Run SQLite integrity and foreign-key checks; compare stable notice/version/link fingerprints, exception checksum, CSV tree, site tree, and state/source coverage between independent runs.
- Compare a staged candidate with published data to expose lost coverage or changed interpretations. Matching old counts is diagnostic, not an acceptance criterion. Promote only a reproducible candidate whose exclusions and material deltas are reported; preserve the prior published artifacts for rollback.

# Public v1 launch audit

Audited 2026-09-23 against the current `reproducible-warn-rebuild` working tree. This is a findings document, not a claim that the current tree is ready to publish. The tree has extensive pre-existing uncommitted changes, so every check below must be repeated on the exact release commit. Priorities: **P0** blocks publication of the data/site as a trustworthy v1; **P1** should be resolved before opening the repository; **P2** is polish or a bounded cleanup decision.

## P0 — data and release integrity

1. **The staged rebuild has not replaced the published data.** `docs/rebuild-progress.md` explicitly says the v7 source-only candidate is an isolated candidate and that source/event decisions and clean-checkout release gates remain open (lines 17–33, 113–119). Its 86,435 notices and 9,006,043 workers are not the checked-in export: `data/exports/warn_notices.csv` has 92,604 data rows. The current export, `data/warn.sql.gz`, and deployed site must not be treated as the accepted source-only build. Complete the gates in `docs/rebuild-contract.md`, explain material state deltas, then promote database, CSVs, health snapshot and site data together.
2. **Known source interpretation questions remain.** `docs/rebuild-progress.md` lists 41 New Jersey old-key fanout groups, 23 repeated-row groups, New York/Iowa/Louisiana held evidence, and Massachusetts/Kentucky receipt-date roles as open work (lines 21, 30–33, 75, 118–119). `docs/next-receipt-date-source-review-2026-09-23.md` documents one Massachusetts filing dated a day before the site's source-table `RECEIVED` value (lines 21–25). Publish only after these are resolved or explicitly bounded as known coverage limits with correctly labeled fields and counts. Preserve source rows and exclusions; do not infer filing identity from name/date similarity.
3. **The advertised source-observation export is empty.** `README.md` lines 18 and 193 promise preserved agency rows with admission/exclusion status. `data/exports/source_observations.csv` currently has only its header (`wc -l` = 1). This is consistent with the candidate not yet being promoted, but it is misleading in a public v1. Regenerate it from the accepted database and reconcile its count with the exception manifest, or remove the claim until available.
4. **Several active source health checks are failing or degraded.** `data/health/health.md` currently reports FL and MA failed for 10 consecutive runs, HI failed for 5, and CO and GA chronically degraded (lines 10–16 and 24). The `active` label and existing notice totals can obscure stale collection. Repair/verify these adapters or mark their coverage and last successful capture clearly in the site and release notes. Recheck health on release day; these values are a snapshot, not a permanent diagnosis.
5. **The full Python test suite fails.** `.venv/bin/python -m pytest tests/ -q` produced **1 failed, 263 passed** on this tree. `tests/test_custom_states.py:29` expects at least 80% of Massachusetts fixture rows to have a notice date, but all 15 now have `notice_date=None`. Align the test with the evidence-based date-role policy and verify the behavior, then rerun on the release commit. Do not fix this by relabeling an agency receipt date as legal notice without source evidence.
6. **A clean, reproducible release commit is still missing.** The working tree contains modified production code/workflows/exports, deleted old code, and untracked replacement docs, bundles, source adapters and tests (`git status --short`). `docs/rebuild-contract.md:17–22` requires a frozen code revision, source bytes, dependency versions, two independent rebuilds, integrity checks and compared output trees. Finish the work in a reviewed commit and run those checks from a fresh checkout. The existing v7 repeatability result is useful but does not cover this combined dirty tree.
7. **Production installation does not use the rebuild lock.** `install.sh:25–39` installs largely unpinned `requirements.txt`, upgrades pip, clones upstream repositories and installs the local package; every CI/deploy workflow runs that script. `requirements-rebuild.lock` and its constraints file were used for isolated diagnostics but are not wired into the production path. Bring CI/deployment onto a documented pinned dependency path and validate it on the target Python version so a later scheduled run cannot silently change its parsers.
8. **Scheduled workflows suppress database-restore failures.** `.github/workflows/scrape-daily.yml`, `scrape-weekly.yml`, and `scrape-adhoc.yml` run `warnlive unpack-db || true` before ingestion. A missing or corrupt dump can therefore be followed by scrape commands against an absent/partial working database; downstream regression checks are useful but should not be the first indication of a failed restore. Make unpacking a hard gate and verify restored database integrity before scraping.

## P1 — public v1 presentation and repository cleanup

9. **Public version metadata still says pre-1.0.** `pyproject.toml:7` and `site/package.json` declare `0.1.0`; the lockfile also carries that version. If the launch is called v1, set the release version consistently to `1.0.0` (or omit a user-visible version entirely if the packages are not distributed), update the lockfile, and tag the accepted commit. SQLite schema version 9 and notice revision labels are internal data versions and should remain accurate.
10. **Internal experiment history would be exposed in a public repository.** The proposed `docs/archive/` and `data/archive/retired-adjudication/` contain pilot plans, model prompts/results and files named `development-v2...` and `candidate-holdout-v2...`; `docs/rebuild-progress.md` and several dated `v4`–`v7` report filenames are working checkpoints. `README.md:111–203` foregrounds an “experimental” rebuild and candidate commands. Keep the evidence needed for reproducibility, but move internal experiment logs and retired model outputs outside the public release tree, replace the top-level README with the accepted v1 workflow, and publish a concise limitations/methodology document. Decide which source bundles are required public evidence rather than deleting them wholesale.
11. **Git history itself exposes prior development.** The current branch has 115 commits, including pilot/adjudication commit subjects (`git rev-list --count HEAD`; `git log --all --grep='pilot\|adjudication' -i`). Removing files in the next commit will not hide them when the repository is made public. If “looks like v1” includes repository history, publish from a new public repository or an intentionally curated initial history after preserving the full private history and checking links/deployment configuration. This is a product/history decision, not a reason to rewrite the working branch blindly.
12. **Tracked machine/build artifacts should be removed.** `.DS_Store` and `site/tsconfig.tsbuildinfo` are tracked (`git ls-files`), and `.gitignore` lacks patterns for both. Remove them from the index and ignore them. `output/temporal-entity-pilot/` is untracked local experiment output; do not add it to the release. Review dated review CSVs, temporary reports and source bundles before staging. `site/dist/` and `site/public/data/` are already ignored as generated output.
13. **The site README's setup command is obsolete.** `site/README.md:10` tells users to `gunzip -kf data/warn.sqlite.gz`, but the repository carries `data/warn.sql.gz` and the supported command is `warnlive unpack-db` (`README.md:14, 92`; `warnlive/cli.py:1302–1330`). Fix this before public onboarding. `site/README.md:21` also says the repository is private, which will become false on launch.
14. **The Methods page claims a SQLite download that is not published.** `site/src/pages/Methods.tsx:237–246` says “CSV and SQLite” at a GitHub repository link, while the checked-in downloadable database is a gzipped SQL dump, `data/warn.sql.gz`. Either publish an actual SQLite download or say “CSV and SQL dump,” with a direct download/restore instruction. Check the full page against the accepted export and source policy before launch.
15. **Retired compatibility remains in production code.** `warnlive/cli.py:1302–1330` still accepts legacy `data/warn.sqlite.gz`; `warnlive/store/db.py:9` preserves older model-cleaning tables, and `warnlive/store/observations.py:55–82` recognizes a legacy input column/status. Audit whether the accepted v1 database or any supported upgrade path still needs each branch. Remove dead paths after proving clean rebuild and upgrade behavior; retain any compatibility that real user data requires and document why it exists.
16. **Pilot and unused UI code remain in the shipped source tree.** `warnlive/enrich/temporal_pilot.py` is an explicit read-only pilot and is only referenced by its test and research docs; `site/src/components/ui/DefRow.tsx` exports `DefRow`/`DefList` with no imports elsewhere. Move the pilot to an internal research area or remove it from the v1 package after deciding whether its dated-evidence work is needed; delete the unused component or use it. This is a targeted finding, not proof that every other module is used.

## P2 — test coverage and launch polish

17. **The frontend test command fails because there are no tests.** `npm test` runs Vitest and exits 1 with “No test files found”; `.github/workflows/test.yml` runs only Python tests. Either add a small number of meaningful route/data-contract tests and run them in CI, or remove the misleading script/dependency. The production frontend build (`npm run build`) does succeed.
18. **The production bundle is large.** Vite reports an 828 kB main JS chunk and an 846 kB county-map chunk before gzip, with a `>500 kB` warning. Measure actual load on the launch site, then split or trim map/chart dependencies if this affects load times. This is a performance follow-up, not evidence of a functional failure.
19. **Public copy and discovery need a final data-backed pass.** `site/index.html:6` hard-codes “44 state portals”; `README.md:4` says “~47 state portals”; `site/src/pages/Methods.tsx:100–109` derives collected/absent counts dynamically. Verify which count is correct for the release dataset and make static metadata agree. Review page title/description and social/link previews after the final build.

## What should stay

- `site/src/pages/NoticeDetail.tsx:73,270–279` shows **versions of a WARN filing**, not “project v2”; hiding those would remove meaningful provenance.
- `site/src/pages/Methods.tsx:152–157` and `StateProfile.tsx:30–35` use “archived” for agency source history. That is a legitimate coverage label. Source snapshots and hashes may be essential to the public reproducibility claim even when internal pilot outputs are removed.
- Keep evidence of exclusions and coverage gaps in a concise public methods/limitations page. A v1 presentation should be accurate about incomplete sources rather than imply full national coverage.

## Checks performed and limits

- Inspected repository status/tracked files, README/docs, site routes/copy, workflows, package metadata, source-observation export and health report; searched source/docs for v2, pilot, deprecated and legacy markers.
- `npm run build`: passed, with the bundle-size warning above. `npm test`: failed because there are no test files. Python suite: 263 passed, 1 failed (Massachusetts assertion above).
- This was a source and local-build audit. It did not verify the live GitHub Pages deployment, run a fresh frozen-source rebuild, audit every agency filing, or assert that all unused Python code has been found. Those gates belong on the final release commit.

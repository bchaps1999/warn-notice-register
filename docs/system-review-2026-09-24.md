# System review and strict replay, 2026-09-24

This review covers the source-only WARN register, its scheduled collectors, identity and admission rules, release exports, and site date displays. It began against the 71,490-notice v1.0.1 release. The verified Kansas and Kentucky candidate has since been promoted into the repository's v1.1.0 release artifacts; see the [release notes](release-v1.1.0-2026-09-24.md). The comparisons below retain the v1.0.1 baseline.

## What the audit found and changed

| Area | Finding | Change in this branch |
| --- | --- | --- |
| Same-key identity | A batch could log action dates more than 45 days apart under one key yet ingest them as versions of one notice. Historical Alabama and other raw rows exercised this path. | Preflight every batch against itself and every stored version. Live runs fail that state without a partial write; the offline raw rebuild holds all rows under each conflicting key and records their source pointers. |
| Collector outcomes | Scheduled and manual jobs could finish green after one state failed because the command allowed successful states to continue. | Persist the selected states and their outcomes; check the report at the end of daily, weekly, and manual jobs so a partial failure is visible while successful state data can still publish. |
| Kansas source breadth | The installed year-search collector supplied 206 portal IDs while the official WARN-filtered listing showed 910. Portal IDs identify rows, but related rows can represent one event or different sites. | Capture all listing and detail pages, hold same-day apparent-event groups and employer-name variants, persist their IDs and signatures for later live runs, and replace the scheduled collector with a complete portal capture. A weekly run must stage at least 700 rows and keeps a source archive. |
| Verification | Missing expected source columns were a warning; a changed schema could silently reduce coverage. An action date in the future could count as a fresh collection. | Missing columns now fail, added columns warn, and source-specific date roles control freshness. Collector last-success age is reported separately and overdue states can open health issues. |
| Release consistency | Counts and a few fields did not catch changes to source links, observations, derived annotations, or individual site detail records. | Regenerate and byte-compare every published CSV and site JSON file against the database and run SQLite integrity and foreign-key checks. The existing checked-in CSV release passes. |
| Site time windows | The latest source date anchored trailing windows; deployment also pinned the site to the last commit day, which could be old after a no-change scrape. Future action dates could enter recent rankings and state lists, and layoff-date fallbacks were not quantified. | Anchor windows to the UTC deployment day, use exact calendar anniversaries, exclude future displayed dates from recent cuts, and show how many records use a layoff date because the notice date is unknown. Offline builds can still pin a date explicitly. |

## Ambiguity and residual risk

Source notice, receipt, posting, and action dates remain separate. A missing legal notice date stays null; the site may use the action date for a displayed month and now labels how often that happens. Worker totals and site allocation stay unresolved when the source cannot support them. A source filing ID alone does not prove that different sites or phases are one event; unlabeled or unmatched amendments remain held. Employer enrichment uses corroborated exact matches and leaves ambiguous identities unmatched.

The 45-day same-key action-date rule is a conservative screen, not proof that every held pair is distinct. It can hold true long-running amendments and cannot resolve two distinct notices with dates closer together. Source-specific review is still needed before releasing held groups. The strict replay was first isolated; the reviewed Kansas and Kentucky stage supplied the data and site build used for v1.1.0.

Kansas's complete portal collector is configured for weekly runs in this branch. It freezes every HTML page and uploads the archive, and it does not infer that a row absent from a partial weekly result ended. The checked-in hold policy and cumulative `data/ks_portal_holds.json` retain unresolved IDs and employer/day signatures across runs. Kansas ingestion checks the complete accumulated policy against existing canonical rows, including when a held portal row disappears from a later capture. Every daily, weekly, and non-smoke ad-hoc publication checks the database against that policy, even when Kansas is absent from the current run. The shared site deployment action applies the same database check to code-only and manual deployments. Weekly and non-smoke ad-hoc workflows preserve new holds before stopping data publication. The v1.0.1 database fails this gate on the held Kansas IDs, while the promoted v1.1.0 database passes. An online deployment still depends on the repository workflow.

**Release sequence:** v1.0.1 contained 27 Kansas IDs that the new source review holds. The repository now pairs the v1.1.0 database and its generated exports, site data, baseline, and collector policy; its Kansas publication gate passes. The old v1.0.1 database must not be paired with the new collector during deployment. A future source page may still revise names, dates, or counts, and matching employer/day is a hold screen rather than proof of duplicate legal filings. Ohio's 2023–25 inventory and the other held-source gaps above remain separate coverage work.
